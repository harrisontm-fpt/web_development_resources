# Session 16 — Presentations, peer evaluation, and handover

[Session index](../README.md) · [Student workshop](workshop.md)

**Week 8 · Three-hour presentation and peer-evaluation session**
**These are opening, transition, and closing notes, not an additional taught lecture.**

## Learning goals

Explain and demonstrate the project, evaluate other applications constructively, and use final feedback to make a verifiable delivery.

## Session schedule

| Minutes | Activity |
| --- | --- |
| 0–5 | Opening instructions and presentation order |
| 5–50 | Three 15-minute slots: presentation under 10 minutes, approximately five minutes of questions, transition |
| 50–60 | Peer-testing instructions and access checks |
| 60–85 | Testing round 1 |
| 85–110 | Testing round 2 |
| 110–120 | Complete feedback forms |
| 120–165 | Triage feedback and make priority fixes |
| 165–180 | Retrospective and final submission actions |

A nine-minute presentation plus five minutes of questions leaves one minute per team slot for transition. Adjust transitions within the first hour while preserving the presentation limit.

## Opening message

Today the teams demonstrate the application as a response to a user problem. Each presentation explains team members, idea, audience, main features, a demonstration, and how to test/find major features. The README may replace slides. Every member participates and is ready to explain their contribution.

The proposal and checkpoints were ungraded formative milestones. The presentation, final application, and supporting evidence inform the final course grade. Passing grades are 1–5; 0 indicates failure. Optional feature count does not automatically earn a higher grade.

Listen for whether the demonstrated behaviour meets the stated need and whether the team can explain the work. Ask questions about evidence, decisions, and tradeoffs, rather than obscure syntax trivia.

## Before peer testing

Each team tests both other applications using the published README and safe demonstration access. Start with the assigned tasks and observe whether the interface makes them discoverable. If a service is unavailable, record the time, steps, and actual result; do not invent a successful test.

Constructive feedback states the task, expectation, actual behaviour, and effect on the user. “The app is confusing” offers little direction. “I could not find the location from the list; I opened three items before discovering it under More” gives the team something to investigate.

Use the required feedback form. Ratings summarise a tester's experience; comments explain the evidence behind the rating. Peer ratings support improvement and are not a numerical voting system that directly determines the course grade.

## Turn feedback into a delivery decision

Prioritise issues that prevent required tasks or public assessment. Assign an owner and verifier. Make small fixes and rerun affected checks. Do not start a large optional feature because someone suggested it in a comment.

If a suggestion is deferred, record why and whether it represents a limitation or a future improvement. Preserve evidence that links observations, changes, and retesting.

## Closing message

Final delivery is due **48 hours after this session ends**, according to the published LMS date/time/timezone. Publish the final GitHub release, verify the public deployment corresponds to it, and submit the release link through the designated LMS point.

The README must make features, setup, testing, and supporting evidence easy to find. Include accessible feedback results and release notes describing post-feedback fixes and known limitations. Every member remains responsible for understanding submitted work.

## Retrospective prompts

What changed from the proposal? Which practice helped delivery? What did each member learn? What would another team need to know to continue the project?

## Preparation and reading

Lecturer: verify presentation order, timing, review access, and the displayed final deadline. Record assessment evidence against the existing descriptors; do not introduce checkpoint marks.
