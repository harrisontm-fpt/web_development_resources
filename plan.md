 # Eight-week Web Project course: 16 sessions

  ## Course approach

  Run this as a project studio alongside WSK: students apply their web development learning to three real briefs while learning how to organise, design, test, and deliver a project.

  Use weeks 1–2 for project management and UX, week 3 for backend application, weeks 4–5 for React, and weeks 6–8 for testing, refinement, and delivery.

  Sessions 1–13 follow your one-hour lecture, one-hour workshop, one-hour project work structure. Sessions 14–15 become support studios; session 16 contains presentations and peer
  testing.

  The proposal and two formal reviews are mandatory but ungraded. The final project, presentation, and supporting evidence inform the final 1–5 grade.

  ## Project management as a weekly practice

  Project management should continue throughout the course, with evidence visible in the work.

  - Trello workflow: Backlog → Ready → In progress → Review/Test → Done. Mark blocked work visibly. Each active card has an owner, acceptance criteria, and a link to relevant code or
    design evidence.

  - Weekly cycle: Set a realistic weekly objective in the first session; demonstrate progress and hold a short retrospective in the second.
  - Project-hour routine: Five-minute team check-in, 45 minutes of focused work, and 10 minutes for board updates and recording the next action. Formal review sessions are exceptions.
  - Scope control: Separate must-haves from stretch features. Every new request records its effect on time and what will be deferred. Changes to client minimum requirements need explicit
    agreement.

  - Shared responsibility: Rotate coordination and review duties. Require everyone to contribute technical work and explain it; assess contribution through code, reviews, design, testing,
    and discussion rather than commit counts alone.

  - Definition of done: A feature meets acceptance criteria, has been reviewed, has appropriate testing, and includes necessary documentation.

  The proposal should be a short document covering the problem, users, MVP, exclusions, wireframes, technical approach, prioritised backlog, milestones, responsibilities, risks, and open
  questions.

  At both formal reviews, every member attends and explains completed work, their contribution, challenges, and next steps. Give teams a short written action list.

  Use the existing grade descriptors: 1–2 for satisfactory delivery of minimum requirements; 3–5 for increasing quality, robustness, completeness, and demonstrated understanding.
  Additional feature count should not determine the grade. The syllabus retains 0 for failure.

  ## Teaching resources, priorities, and assumptions

  Reuse WSK selectively: Weeks 1–2 supply refresher material; week 3 supports backend work; weeks 4–5 support React; the project materials support testing and deployment. Adapt exercises
  to each team’s domain.

  Prepare short new resources for team agreements, Trello, scope control, proposals, wireframing, usability testing, and review checklists. These are the main additions beyond the
  technical reference course.

  Three teaching priorities deserve particular attention:

  - Connect design to implementation. Have students move from wireframes to a component hierarchy and identify the minimum necessary state, following Thinking in React
    (https://react.dev/learn/thinking-in-react).

  - Build accessibility into normal UI work. Teach labels, instructions, and usable error feedback alongside forms, using the W3C forms tutorial (https://www.w3.org/WAI/tutorials/forms/).
  - Test meaningful behaviour. Base browser tests on user journeys and observable outcomes, following Playwright’s testing guidance (https://playwright.dev/docs/best-practices).

  Keep advanced state libraries, elaborate animations, optional uploads, and extensive infrastructure automation as brief-dependent extensions. Protect time for essential functionality,
  testing, and delivery.

  Planning assumptions:

  - WSK follows the supplied sequence alongside this course. Coordinate within each week so project exercises follow its relevant lessons.
  - Usable briefs arrive by the end of week 1. Use a small practice brief in the opening workshop if needed; record unresolved client details as assumptions.
  - Students undertake the syllabus’s six or more hours of independent work per week, including implementation, reading, and testing.
  - Reviews occur in weeks 4 and 7, resolving the conflict with the syllabus’s week 5 entry.
  - Before teaching, align the syllabus and assignment wording with the ungraded milestones, studio-session exceptions, and final deadline 48 hours after session 16.
